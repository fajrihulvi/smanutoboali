# S25 — Payment gateway (Midtrans)

## Rencana

1. `PaymentGateway` (interface) + `MidtransGateway` (Snap API lewat HTTP client Laravel, config `services.midtrans` dari `.env`, sandbox/production).
2. Tabel `gateway_transactions` (satu baris per percobaan bayar: order_id unik, nominal, token Snap, status, tautan ke payment bila lunas) dan `payment_callbacks` (setiap callback mentah + hasil verifikasi signature).
3. Orang tua klik **Bayar online** → `POST /orang-tua/keuangan/{tagihan}/bayar` membuat transaksi (order_id baru tiap percobaan) → popup Snap → halaman status.
4. Webhook `POST /webhooks/midtrans`: dikecualikan dari CSRF, verifikasi `signature_key` (SHA512 order_id+status_code+gross_amount+server key), cek nominal, proses **idempotent** dengan row lock:
   - `capture`(accept)/`settlement` → Payment GATEWAY CONFIRMED + kwitansi → tagihan dihitung ulang (PAID);
   - `pending` → tagihan PENDING;
   - `expire`/`cancel`/`deny`/`failure` → transaksi gagal → tagihan FAILED (bisa dicoba lagi).
   Orang tua dan operator diberi tahu.
5. Halaman status membaca status dari DB (auto-refresh selama menunggu). Status dari redirect/JS Snap **tidak pernah** dipercaya.
6. CSP untuk domain Midtrans dicatat untuk S32.
7. Test: signature salah ditolak, callback ganda tidak menggandakan pembayaran, settlement → PAID, expire → FAILED, pending → PENDING, nominal tidak cocok ditolak, orang tua lain tidak bisa membayar.

## Keputusan

- Tanpa SDK Midtrans. Cukup dua hal (buat transaksi Snap & verifikasi signature), memakai `Http` Laravel sehingga mudah diuji dengan `Http::fake`.
- **Pembayaran online selalu untuk sisa tagihan penuh.** Cicilan tetap lewat bukti transfer/TU.
- Tombol "Bayar online" hanya tampil bila server key & client key terisi, tagihan masih bisa dibayar, dan tidak ada bukti transfer yang menunggu verifikasi.
- Bila transaksi online lunas tetapi sisa tagihan sudah berkurang (mis. operator mencatat pembayaran manual di sela waktu), pembayaran tetap dicatat (uang sudah diterima) dengan catatan **kelebihan bayar** untuk ditindaklanjuti operator.
- Callback dengan signature salah dicatat (`signature_valid = false`) lalu dijawab 403. Order tidak dikenal dijawab 404. Selain itu 200, supaya Midtrans tidak mengulang callback yang sudah diproses.
- Percobaan bayar yang ditutup sebelum memilih metode (tanpa callback) tetap berstatus CREATED dan tidak memengaruhi tagihan.

## Hasil

- `PaymentGateway` (kontrak) + `MidtransGateway` (Snap via `Http`, sandbox/production dari `.env`, signature SHA512 dengan `hash_equals`), di-bind di FinanceServiceProvider.
- Tabel `gateway_transactions` (order_id `SKL-<ULID>` unik per percobaan) dan `payment_callbacks` (payload mentah + validitas signature + hasil proses). Enum `GatewayStatus` dengan `fromMidtrans()` dan `canTransitionTo()`.
- `StartOnlinePaymentAction` (sisa penuh, ditolak bila ada bukti transfer menunggu / gateway nonaktif) dan `HandleGatewayCallbackAction` (log → signature → nominal → row lock → transisi idempotent → Payment GATEWAY + kwitansi / FAILED / PENDING → notifikasi orang tua & operator + audit).
- `InvoiceBalance` kini memperhitungkan transaksi online PENDING dan kegagalan gateway (FAILED tidak lagi "menempel" setelah ada pembayaran lain).
- Webhook `POST /webhooks/midtrans` (dikecualikan dari CSRF, throttle 120/menit): 403 signature salah, 404 order tidak dikenal, 422 nominal tidak cocok, selain itu 200.
- Orang tua: kartu **Bayar online** (hanya bila kunci Midtrans terisi) → Snap popup (snap.js dimuat saat diklik; fallback ke halaman redirect Midtrans) → halaman **Status pembayaran** yang membaca DB dan auto-refresh sampai final, lengkap dengan tautan kwitansi.
- `.env.example`: catatan URL notifikasi `https://<domain>/webhooks/midtrans`. CSP untuk `app(.sandbox).midtrans.com` dikerjakan di S32.
- 509 test Pest (7 baru untuk Midtrans) + 27 Vitest lulus; pint, phpstan, eslint, prettier, tsc, dan build hijau.
